# Design: Bonsai integration — listener transport + slice 1 (materials push)

Date: 2026-08-27
Status: Approved (brainstorming session)

## Goals

GUI-driven integration with [Bonsai](https://bonsai.ifcopenshell.org): the
materialsdb web UI stays the picker; a Bonsai-side listener receives pushes
and applies them to the IFC model currently open in Bonsai.

Slice 1 (this spec): fix the shared GUI⇄Bonsai transport, then push picked
materials from the picker page — registering `IfcMaterial` entities (+ the
materialsdb identity and per-layer psets) into the active project's material
library. Assigning them to objects stays a normal Bonsai action.

Planned follow-up slices, each shipping independently behind the same
channel: (2) push a construction from the construction maker, creating the
matching type element per `design_usage` — wall → `IfcWallType`,
floor → `IfcSlabType`, roof → `IfcRoofType`, generic → all three sharing one
`IfcMaterialLayerSet`; (3) round-trip edit of an existing layer set from the
open model inside the composer.

## Decisions

- **Standalone Blender extension in this repo first** (`bonsai_addon/`,
  Blender 4.2+ extension format with `blender_manifest.toml`, installed as a
  zip). Chosen over contributing directly into Bonsai core for iteration
  speed; the insert logic is kept as a thin adapter so a later upstream
  contribution is mostly UI re-plumbing. Maintainer is a Bonsai developer —
  upstream is the likely end state once proven.
- **Transport: short polling.** The add-on polls the server every ~1s
  (`bpy.app.timers`); a push is queued server-side on demand and picked up by
  the next poll (≤1s latency). Chosen over long-polling/websockets: stdlib
  server stays dependency-free, no parked handler threads, trivially
  testable. Polling is fully decoupled from editing time — nothing is sent
  until "send" is clicked, and an idle poll is a sub-millisecond local `204`.
- **Discovery file, zero-config.** The GUI writes
  `<cache.get_cache_folder()>/gui.json` (`{port, token, pid}`) at startup and
  removes it on clean shutdown. NOT a literal `~/.cache` path — the cache
  helper already resolves `%APPDATA%\materialsdb` on Windows and
  `$XDG_CACHE_HOME`/`~/.cache` elsewhere. Any number of Blender instances
  read the same file; if two GUI servers run, the last one started wins (pid
  recorded for debugging). A stale file after a kill is benign: the add-on
  reports "not reachable" and the next GUI start overwrites.
- **Multi-instance targeting.** Each listener registers with the server
  (`client_id` + the open model path). The GUI shows connected listeners and
  the send action targets one of them.
- **Register-only semantics.** A push creates the materials in the project's
  material library; it never touches object assignments.
- **Resolved-JSON split.** The server resolves picks into fully-specified
  payloads at send time (reusing `material_builder.py`'s `PSETS`/`get_value`/
  `clean_psets` and the configured country); the add-on is a dumb mapper
  from payload to ifcopenshell/bonsai calls. No business logic crosses the
  wire; the add-on never needs the `materialsdb` package.

## Architecture

```
Browser (app.js) ──POST /api/listener/send──▶ materialsdb-gui server ──┐
                                                                       │ pending queue
Blender/Bonsai add-on ──GET /api/listener/poll (every ~1s)─────────────┘
        │ payload → ifcopenshell.api into the ACTIVE Bonsai model
        └──POST /api/listener/status ("applied" / "error: …")
```

Server state stays in-memory on `GuiState`:
`listeners = {client_id: {model_path, last_seen, pending, last_status}}`.
A listener silent for >5s (no polls) is pruned. One pending payload per
client; `poll` returns and clears it (at-most-once). All endpoints are
token-gated; the add-on authenticates with the token from `gui.json`.

## Listener API

| Endpoint | Purpose |
|---|---|
| `POST /api/listener/register` | `{client_id, model_path}` → announce + attach (`client_id` is a uuid generated by the add-on at startup) |
| `GET /api/listener/poll?client_id=X` | pending payload or `204`; refreshes liveness |
| `POST /api/listener/send` | `{client_id, payload}` queue one push |
| `POST /api/listener/status` | `{client_id, status, detail?}` — surfaced in the GUI |
| `GET /api/listener/clients` | connected listeners (id, model_path, last status) for the GUI dropdown |

## Slice 1 payload

The server resolves a pick into exactly the entity list `MaterialBuilder`
would create — **one entry per `IfcMaterial`** (a 2-layer material pick
yields 2 entries with the same name, exactly like the standalone `.ifc`
export today). The add-on creates them entity-for-entity:

```json
{"action": "add_materials", "materials": [{
  "source_id": "00000000-…-0001", "layer_id": "00000000-…-00a1",
  "name": "Isolant A", "description": "Panneau isolant",
  "category": "Insulation", "color": 16711680,
  "identity": {"material_id": "00000000-…-0001", "company_id": "…",
               "company": "Mini SA"},
  "psets": {"Pset_MaterialThermal": {"ThermalConductivity": 0.036}},
  "layer": {"layer_id": "00000000-…-00a1", "thick_m": 0.2}
}]}
```

`psets` are the per-entity, country-resolved values (identity pset included
via `identity`); `layer` carries the `IfcMaterialLayer` data (thickness in
meters, source layer id in `Description`), matching the export path's
layer+set creation. Values mirror what `MaterialBuilder.build()` writes
today (same `PSETS` resolution, unit factors, configured country), which
makes the CI equivalence test direct: resolved payload ≡ builder output for
the same fixture material. `color` carries the raw XML decimal; the add-on
applies it as a best-effort surface style, never fatal on failure.

## Add-on layout

```
bonsai_addon/
├── blender_manifest.toml
├── __init__.py      # bpy operator + panel + polling timer (the only bpy/bonsai imports)
├── discovery.py     # read gui.json, register, poll loop (stdlib only)
└── insert.py        # PURE ifcopenshell mapping: payload → entities (no bpy imports)
dev_utils/build_bonsai_addon.py   # zip for 'Install from Disk'
```

`insert.py` imports only `ifcopenshell` (+`ifcopenshell.api`), so CI tests it
against a scratch IFC — the `[ifc]` extra already ships ifcopenshell to CI.
Insertion goes through bonsai's tool/API layer so its UI refreshes properly;
the exact binding (`bonsai.tool.*` vs raw api calls + UI refresh) is settled
during implementation by the maintainer.

## GUI UX

Picker page: a "send to Bonsai" control next to the export actions, fed by
`/api/listener/clients` — disabled with "no listener" when none connected,
a target dropdown when several are, and per-send result feedback
("applied ✓" / error detail) from the status endpoint.

## Error handling

- Unknown/stale `client_id` on send → `404`; GUI refreshes the client list.
- Add-on failing to insert → status `error` with the exception message; the
  pending payload was already consumed, so nothing re-fires on the next poll.
- Unauthorized calls → `403` like every other mutating endpoint.
- GUI server down → add-on timer keeps retrying quietly and shows
  "materialsdb-gui not reachable"; it re-registers when reachable again.

## Testing

- Server: `tests/test_gui_server.py` — register/poll/send/status/clients
  lifecycle, token enforcement, stale-client pruning, poll-clears-pending,
  404 on unknown client, and payload-resolution equivalence against
  `MaterialBuilder` output for a fixture material.
- Add-on mapping: CI tests for `insert.py` against a scratch `ifcopenshell`
  file (entity counts, identity pset values, layer psets, idempotent
  re-insert).
- Blender UI (timer, panel, targeting): manual checklist, consistent with
  project practice.

## Cross-platform

Verified Linux/macOS/Windows: stdlib-only server; discovery path via
`cache.get_cache_folder()`; add-on uses only bpy/bonsai/ifcopenshell and
stdlib; loopback HTTP adds no firewall surface beyond what the GUI already
has.

## Future hooks

Slices 2–3 reuse the channel with new `action` values (envelope fixed here);
`/api/listener/*` is host-agnostic, so FreeCAD/Revit listeners can reuse it
unchanged. Upstream Bonsai contribution would replace only the add-on UI
layer.
